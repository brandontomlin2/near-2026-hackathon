# Audit: contracts/personality-nft

Scope: `contracts/personality-nft/src/lib.rs` (near-sdk 5.30, near-contract-standards 5.30).
Method: manual review against the NEAR audit checklist, plus unit tests for every
finding below (`cargo test` in the contract dir, 66 tests). No transactions were
sent and no keys were used.

**State layout:** the contract state layout changed in audit 2 and its follow-ups (`seen_hashes`, `in_flight` holding a per-transfer nonce, `next_lock_nonce`; the lock's block height was dropped again in audit 3). Nothing is deployed yet, so no migration is needed.

Public method names are unchanged. `anchor_sheet` and `nft_mint` gained new
panic conditions (listed below); their signatures are the same.

## Findings

| # | Severity | Location | Finding | Status |
| --- | --- | --- | --- | --- |
| 1 | Medium | `nft_mint` | No bounds on `token_id` or any `TokenMetadata` string. A mint could store arbitrarily large metadata, bloating storage and making every `nft_token` / `nft_tokens` view (and the viewer that calls it) heavy. `extra` could also be non-JSON, breaking consumers that parse traits. | Fixed: token_id 1-64 bytes, title 128, description 1024, extra 2048 and must be a JSON object, media/reference/date strings 512. |
| 2 | Medium | `anchor_sheet` | Re-anchoring the same hash still bumped `memory_depth`, so the owner could inflate the token's "reputation" for 1 yoctoNEAR without any new sheet. A seller could pump depth before a sale. | Fixed: re-anchoring the current hash panics. |
| 3 | Low | `anchor_sheet` | Owner can still alternate between two hashes to raise depth. Depth proves "anchored N times", not "N genuine summaries". | Fixed (audit 2, M3): a hash can be anchored once per token, so alternating A, B, A, B is rejected. Depth is still advisory (no sheet contents on chain). |
| 4 | Low | `anchor_sheet` / sale flow | Front-running a sale: the seller can anchor a different sheet just before `nft_transfer`. The buyer's pre-trade check can go stale. | Mitigated (audit 2, M2): `nft_transfer_expecting_anchor` reverts if the anchor differs from the expected `(hash, depth)`; README tells buyers to pin the anchor. |
| 5 | Low | `new` / `new_default_meta` | Initialization is public. Whoever calls it first picks the owner. `#[init]` blocks a second call, but deploy and init must be one batch. | Operational: deploy with `--initFunction new_default_meta` (testnet-deploy). |
| 6 | Low | contract | `owner_id` (minter) is immutable; no rotation. A lost key means no more mints. Existing tokens are unaffected. | Accepted for a hackathon. |
| 7 | Info | views | `nft_tokens*` take a caller-chosen `limit`; a huge limit only affects the caller's own view call. | No change. |
| 9 | Low | `validate_token_metadata` | `media_hash` / `reference_hash` were unbounded `Base64VecU8`, allowing view bloat (self-grief by the minter). | Fixed: each must be `None` or exactly 32 bytes (sha256). |
| 10 | Low | `scripts/testnet-deploy.mjs` | `deploy --send` defaulted the contract account to `NEAR_ACCOUNT_ID`, which could overwrite the owner's personal account code. | Fixed: `deploy --send` requires an explicit `NEAR_CONTRACT_ACCOUNT_ID`; dry-run unchanged. |
| 11 | Info | `validate_token_id` | Contract accepted any 1-64 byte id; JS builders only accept `[a-z0-9_-]`. | Fixed: contract now enforces the same charset. |
| 12 | Info | contract | Follow-up audit notes, no change: no owner rotation/migration (see #6); validation order in `anchor_sheet` runs hash/deposit checks before the ownership check (harmless); refund dust of <= 1 yocto per call is kept by the contract; JS first-anchor deposit (0.01 NEAR) is generous but excess is refunded; mint deposit (0.05 NEAR) is refunded minus storage. | No change. |
| 13 | Medium | `nft_transfer_call` / `anchor_sheet` | The receiver owns the token during `nft_on_transfer` and could re-anchor, then revert the transfer, leaving the original owner with a tampered anchor. | Fixed (audit 2, M1): the token is frozen for `anchor_sheet` while in flight (cleared in `nft_resolve_transfer`); a nested `nft_transfer_call` is rejected. Follow-up: the lock stores its block height and expires after `IN_FLIGHT_EXPIRY_BLOCKS` (1000, about 17 minutes), so a failed `nft_resolve_transfer` callback cannot freeze the anchor forever. Follow-up 2 (fixed): a late callback of an earlier transfer could clear the lock of a later one. Each lock now stores a per-transfer nonce (`next_lock_nonce`, wrapping, never panics). `nft_transfer_call` is reimplemented on `internal_transfer` and keeps the NEP-171 callback shape: it schedules the standard `nft_resolve_transfer` (unchanged name, signature and 5 Tgas budget, so wallets and indexers that match on it keep working) and chains a second private callback, `release_lock(token_id, nonce)` (10 Tgas, see #19), after it. The standard callback's fixed arguments leave no room for the nonce, so the chained callback carries it: it clears the lock only if the stored nonce matches, never panics, and forwards the resolve result as the NEP-171 bool (a resolve that ran out of gas counts as completed, since ownership was not rolled back). A stale callback still settles its own transfer but leaves a newer lock alone. `nft_resolve_transfer` never touches the lock. Cost: 8 more bytes per lock, freed on clear. Follow-up 3 (audit 3, M-1, fixed): the block-height expiry reopened this item. Wall-clock delay on NEAR is not block-bounded: a receiver's `nft_on_transfer` can chain `promise_yield_create` callbacks (each waits up to ~200 blocks) or congested cross-contract hops and stall resolution past 1000 blocks (the stall is bounded only by the gas the sender attached, which every chained call spends, so it is finite but can run far past any fixed window), then anchor as the recorded owner, then return the token with a poisoned anchor the previous owner can never undo (the hash is burned in `seen_hashes`). The expiry and the lock's `set_at` field are removed; the lock is cleared only by `release_lock`, which the runtime always executes once the receiver's promise settles, however it ends (it is `#[private]`, 10 Tgas, one lookup, one remove, one 8-byte result read, no panic path). The nonce check stays: it guards a stale or replayed callback of an earlier transfer arriving while a later transfer's lock is set. Tests: `receiver_cannot_anchor_at_any_height_while_locked` (the attack, inverted: at heights 1000, 1999, 2000, 11000 and `u64::MAX` the receiver can neither anchor, nest a transfer call nor sell with a pinned anchor; after the return the owner's anchor is untouched and the planted hash is still anchorable), `stale_callback_cannot_clear_a_later_transfers_lock` (rewritten without the expiry), plus the earlier `transfer_call_schedules_standard_resolve_then_release_lock_with_its_nonce` and `release_lock_forwards_resolve_result_and_survives_a_failed_resolve`. |
| 15 | Low | `release_lock` | (audit 3, L-1) A failed `nft_resolve_transfer` receipt (only possible by exhausting its fixed 5 Tgas, the SDK's own budget) is forwarded to the caller as `true`. Ownership was not rolled back, so the token is with the receiver, but the previous owner's approvals were dropped without being restored and the caller is told the transfer completed. | Documented: the contract must not panic in `release_lock` (that would re-lock the token), so callers that need to tell this case from a receiver that kept the token read the receipt outcomes of `nft_resolve_transfer`. |
| 16 | Low | `nft_transfer_call` | (audit 3, L-2) A second `nft_transfer_call` on a token whose first one has not resolved panics. NEP-171 does not forbid it; a stock contract lets the resolve callback detect "owner moved" and no-op, so an escrow that forwards the token with `nft_transfer_call` from inside `nft_on_transfer` fails here. | Documented as a deliberate deviation (one lock per token keeps the frozen-anchor invariant simple). The window lasts until `release_lock`. |
| 17 | Low | `nft_transfer_call` | (audit 3, L-3) `nft_transfer_call` takes exactly 1 yocto, so the lock's storage (prefix, token id, 8-byte nonce; about 80 bytes) is paid from the contract account's balance until `release_lock` frees it. Bounded by `total_supply × ~80 B` (only the owner mints, one lock per token), so not a drain, but with every token in flight at once the pinned balance is about 0.008 NEAR per 100 tokens. If the contract balance cannot cover the write, `nft_transfer_call` fails for everyone. | Documented: keep the contract account funded with a buffer proportional to supply. Charging the caller would break the 1-yocto requirement. |
| 18 | Low | views / `nft_transfer_expecting_anchor` | (audit 3, L-4) `sheet_anchor` and `nft_token` looked identical for a locked and an unlocked token, and `nft_transfer_expecting_anchor` accepted an in-flight token whose pending `nft_resolve_transfer` could still hand it back to the previous owner. | Fixed: new view `nft_in_flight(token_id) -> bool`; `nft_transfer_expecting_anchor` panics while the token is in flight. Tests: `nft_in_flight_view_tracks_the_lock`, `transfer_expecting_anchor_refuses_an_in_flight_token_and_works_after`. |
| 19 | Low | `GAS_FOR_RELEASE_LOCK` | (audit 3 follow-up) `release_lock` had a 5 Tgas static budget with no margin over the SDK's own 5 Tgas for the comparable `nft_resolve_transfer`. It is the only thing that clears a lock, so a budget shortfall after a fee change would leave the token locked forever (the sender would have to resend). | Fixed: raised to 10 Tgas; unused static gas is refunded, so the margin is free. `transfer_call_schedules_standard_resolve_then_release_lock_with_its_nonce` pins the literal 10 Tgas on the receipt. No sandbox (near-workspaces) test asserting the real burn: the crate has no near-workspaces dependency and adding one pulls a large dependency tree plus a network download of the sandbox binary at first run, which the offline, keyless `cargo test` promise in the README rules out. The callback does one `LookupMap` get, one remove and one 8-byte `promise_result_checked` read, strictly less work than the SDK's `nft_resolve_transfer` (owner read and write, approvals restore), which the SDK fits in 5 Tgas; 10 Tgas therefore leaves a margin of at least half. Re-check with a sandbox run if the callback ever grows. |
| 20 | Info | docs / tests | (audit 3 follow-up) README and this file said the receiver "can stall as long as it likes"; the stall is bounded by the gas the sender attached (finite, but not block-bounded). The height loop in `receiver_cannot_anchor_at_any_height_while_locked` did not say it guards against reintroducing an expiry. The tests-added line below counted 43 while the header said 66. | Fixed: wording corrected in the README, in this file and in the contract doc comments; the test's doc comment names the loop as a regression guard; counts below match `cargo test`. |

## Checked and found sound

- **Mint auth**: only `owner_id` can mint (test: `mint_by_non_owner_panics`).
- **Token id collisions**: duplicate id panics before any write; the existing
  owner and anchor are untouched (`duplicate_mint_cannot_reset_anchor_or_owner`).
  `LookupMap` keyed by token id with a distinct `StorageKey` prefix, no prefix collisions.
- **Storage deposits**: the minter pays for token + anchor storage, the excess is
  refunded to the minter (not the receiver), and `internal_mint_with_refund(.., None)`
  is used so the refund happens once (`mint_charges_exact_storage_and_refunds_the_rest`,
  `anchor_refunds_excess_deposit_to_the_token_owner`). Insufficient deposit panics
  (`mint_with_half_the_storage_cost_panics`, `first_anchor_with_only_one_yocto_cannot_cover_new_storage`).
- **Transfer**: needs exactly 1 yocto, owner or an approved account with the right
  approval id; transfer to self rejected; approvals are cleared on transfer so a
  previous spender cannot take the token back.
- **Approvals**: only the owner can approve/revoke; revoked accounts lose the right
  to transfer; an approved account cannot approve others.
- **Sheet-hash anchoring permission**: only the *current* token owner. Not the
  contract owner, not an approved account, not the previous owner after transfer.
  The anchor is keyed by token id so it follows the token. Hash must be
  64 lowercase hex chars. Requires >= 1 yocto, which excludes function-call keys.
- **Arithmetic**: `memory_depth` uses `checked_add`; release profile has `overflow-checks = true`.
- **Reentrancy / callbacks**: no cross-contract calls added beyond the standard
  `nft_transfer_call` / `nft_approve` flows.
